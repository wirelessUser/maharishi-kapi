# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm start           # ng serve — dev server at http://localhost:4200, live reload
npm run build        # ng build — production build + SSR bundle to dist/maharishi-kapi/
npm run watch        # ng build --watch --configuration development
npm test             # ng test — runs the Vitest suite (jsdom environment)
node dist/maharishi-kapi/server/server.mjs   # run the built SSR server (after `npm run build`)
```

- There is no `lint` script and no ESLint/Prettier config wired into the CLI — don't assume one exists.
- To run a single spec file: `npx vitest run src/app/components/<name>/<name>.spec.ts`. Specs are Angular CLI's default scaffolded `TestBed`/"should create" tests for every component — they are not meaningful behavioral coverage; don't treat a passing `npm test` as proof a feature works.
- Always verify a change with `npm run build` (this is a prerendered SSR app — `ng build` performs full static generation for every route and will catch template/type errors that a dev-server hot-reload can hide). Check the summary line for `Prerendered N static routes` and 0 errors/warnings.
- The production bundle budget in `angular.json` (`architect.build.configurations.production.budgets`) is currently raised above the Angular CLI default because real content pushed past it — if a build starts failing on the initial-bundle budget after adding content, that's expected pressure, not a bug; raise it deliberately rather than treating it as a regression to reverse.

## Architecture

**Angular 22, standalone components only (no NgModules).** Every component/page declares its own `imports: [...]` array on the `@Component` decorator. Routing uses the new signal/control-flow style: templates use `@if` / `@for` (not `*ngIf`/`*ngFor`), except `theme-customizer.html` which still uses the legacy `*ngIf` + `CommonModule`/`FormsModule` — that's the one intentionally-older component, not a pattern to copy elsewhere.

**SSR + full prerendering, not a SPA-only app.** `@angular/ssr` renders every route to static HTML at build time (`src/server.ts` is the Express SSR entry; `src/app/app.routes.server.ts` controls per-route render mode). All routes default to `RenderMode.Prerender`. **Dynamic routes must supply `getPrerenderParams`** or the build can't know what to prerender — see the `retreats/:slug` entry in `app.routes.server.ts`, which pulls its param list straight from the `RETREATS` data array. Follow this pattern for any new `:param` route. Route params are read via Angular's `input()` signal binding, not `ActivatedRoute` — `withComponentInputBinding()` is enabled in `app.config.ts` for this.

**Design tokens live in `src/styles.css`, not a `tailwind.config.js`.** This is Tailwind v4's CSS-native config: colors, fonts, and shadows are declared inside an `@theme { }` block using `--color-kapi-*`, `--font-*`, `--shadow-*` variables, which Tailwind then exposes as ordinary utility classes (`bg-kapi-purple`, `shadow-premium`, etc.), including opacity-modifier syntax (`bg-kapi-purple/10`). **This is the single source of truth for the brand palette** — retuning the hex values there cascades across the entire site instantly; there is no need to touch individual component templates to reskin. The palette was deliberately chosen for a Vedic astrology/spiritual brand (deep cosmic violet, sacred saffron, sindoor rose/maroon, temple gold, warm ivory) — don't drift back toward generic bright SaaS colors or raw Tailwind palette classes (`purple-500`, `rose-500`, etc.) in new markup; use the `kapi-*` tokens so a future palette change stays centralized. A few custom keyframe utilities (`animate-spin-slow`, `animate-pulse-slow`) are also hand-declared in this file since they aren't Tailwind defaults.

**Page vs. component split:**
- `src/app/pages/*` — one folder per route (`home`, `courses-page`, `services-page`, `about-page`, `blog-page`, `retreats-page`, `retreat-detail-page`). Registered in `src/app/app.routes.ts`.
- `src/app/components/*` — section-level building blocks. Most are composed together inside `pages/home/home.ts`'s `imports` array in a specific stacking order (hero → stats → featured courses → legacy → roles → journey → immersive → consultation → stories → downloads → instagram); a few (`top-bar`, `navbar`, `footer`, `whatsapp-btn`, `theme-customizer`) are mounted globally once in the root `app.html`/`app.ts` shell and appear on every route regardless of the router outlet's content.

**Data-driven content pattern (`src/app/data/`).** Retreats live in `src/app/data/retreats.ts` as a typed `Retreat[]` array plus a `getRetreatBySlug()` lookup, consumed by both `retreats-page` (listing) and `retreat-detail-page` (detail, driven by the route param). This is the model to extend for any future list+detail content type — don't inline a second copy of the data into the detail page. (Blog articles are currently the exception: they're inlined directly in `blog-page.ts` rather than extracted to `data/`, which is worth normalizing if the blog grows a detail-page route.)

**Site content mirrors the real business (maharishikapi.com) — treat it as production copy, not placeholder.** Founder name/bio (Acharya Alok Awasthi), the course catalog and USD pricing, consultation service names, social links (Instagram/YouTube/Threads — not Facebook/Twitter), and the press logos were all pulled from the live site and are considered accurate. Photos of the founder and the institute logo are downloaded into `public/images/` (not hotlinked) for reliability — reuse those existing files (`founder-alok.jpg`, `founder-alok-nature.jpg`, `founder-alok-group.jpg`, `mk-logo.png`, `inkhbar-logo.png`, `agniban-logo.jpg`) rather than reintroducing a generic stock photo when a person or the brand needs to appear. Don't casually invent new fictional stats, testimonials, or pricing to fill a section — prefer sourcing from the real site (WebFetch it) or asking, since prior placeholder content in this project has had to be found and replaced after the fact.

**Every meaningful photo must be a real `<img>` tag, not a CSS `background-image` div.** This is required for the Theme Customizer's image tools (see below) to work uniformly. The only sanctioned exception is the `stardust.png` sparkle texture (used in a few hero sections) — it's a tiling/repeating decorative pattern, and `<img>` can't repeat its content the way `background-repeat` does, so it's kept as a CSS background intentionally. When adding a new decorative photo, use `<img class="absolute inset-0 w-full h-full object-cover ...">` inside a `relative overflow-hidden` container, matching the existing hero-image pattern.

**External images (Unsplash) must be link-verified before use, not guessed.** Multiple past incidents in this project involved an assumed Unsplash photo ID actually depicting something else entirely (wrong crop, wrong subject). Before adding a new external image URL, verify it resolves — either via a HEAD request (`curl -s -o /dev/null -w "%{http_code}" "<url>"`) or by fetching/viewing it — rather than constructing an ID from memory.

**Theme Customizer (`components/theme-customizer`) is an in-browser, session-only visual editor, not a CMS.** It's mounted globally and toggled via a floating "Build" button. It has no backend and no persistence (not even `localStorage`) by explicit design decision — all edits (text, colors, spacing, and image focal-point/zoom/rotate/replace-via-upload) are applied live to the DOM via `Renderer2` and vanish on page refresh. It works by an inspector click-to-select mode (`toggleInspector` / global click listener) that lets you click any element on the page, then reads/writes inline styles for the selected element, with its own undo stack (`history[]`). Image controls detect either a real `<img>` (uses `object-position` + `transform: scale/rotate`) or a `background-image` div (uses `background-position` + `background-size`, since scaling the div itself via `transform` would distort its layout box) — see `isImg()` / `hasBackgroundImage()` in `theme-customizer.ts`. If this is ever extended to persist changes (e.g., a future .NET backend for real image uploads), that's a deliberate architecture change to discuss first, not an assumption to bake in silently.
